# RP2040 (Raspberry Pi Pico) firmware

Status: **implemented, compiles, host-tested; not yet validated on hardware.**
Flashing, motor movement and pulse timing on a real Pico are **unverified**
until the procedure in [§9](#9-hardware-validation) has been carried out.
The board is marked `provisional` in `motioncore firmware targets`.

## 1. Architecture

The RP2040 runs the same shared firmware as the STM32F411 and the virtual
MCU. Only the board crate is new:

```text
boards/rp2040 ─────────┐   boards/stm32f4 ──┐   crates/simulator ──┐
  TIMER alarm tick      │     TIM3 tick      │     tokio tick        │
  USB CDC, watchdog     │     USB CDC, IWDG  │                       │
  PIO STEP/DIR (6 SMs)  │     GPIO STEP/DIR  │                       │
                        ▼                    ▼                       ▼
                 firmware-core   (protocol, watchdog, faults, status — shared)
                        │
                 firmware-stepper (segments, homing, stop, limits — shared)
                        │
                 firmware-hal     Hal trait (+ flush_pulses hook)
                        │
  firmware-pio-step ◀───┘ (RP2040 only: PIO program, command encoding, step buffering)
```

The host (engine, planner, MCU manager) does not know which MCU it talks
to. It sees the same protocol, segment format, fault codes and identity
message from every board. The engine checks the reported board id against the
configuration and refuses a mismatch.

### Motion scheduling vs. pulse execution

* **Scheduling (shared, unchanged):** `StepperAxis::tick` interprets the
  current segment, tracks position, checks soft limits and endstops before
  every step, detects queue underrun and late segments, and handles homing
  and controlled stop. It calls `Hal::step` once per step that became due.
* **Pulse execution (board specific):**
  * STM32F411 / simulator: `Hal::step` emits the pulse immediately.
  * RP2040: `Hal::step` only records the step in a per-axis buffer
    (`StepRuns`, at most 4 direction runs per tick). At the end of the tick,
    `Hal::flush_pulses` turns each axis' buffer into PIO commands that
    spread those steps **evenly over the next tick window**. Overdue steps
    never go out as a burst.

The `flush_pulses` hook has a default no-op implementation, so the STM32F411
and the simulator behave exactly as before.

### Single core

Core 0 runs everything: the tick interrupt (`TIMER_IRQ_0`, every 200 µs) and
the main loop (USB, frame decoding, status, watchdog). Core 1 is parked.

Reasons:

* `McuCore` owns commands and motion together. Splitting it across cores
  would need cross-core queues and a second owner of axis state, for no
  benefit unless one core is too slow.
* The PIO does the time-critical part (pulse edges). The CPU only has to
  produce one command word per axis per 200 µs.

This must be confirmed by measuring the tick interrupt duration with six
axes moving ([§9](#9-hardware-validation)). If it uses more than about half
of the 200 µs window, moving the tick to core 1 is the next step.

puts channel 1's STEP on GP3 is rejected with

## 4. PIO design

### State machine allocation

* One state machine per axis: axes 0–3 use PIO0 SM0–3, axes 4–5 use PIO1
  SM0–1 (`sm_for_axis`). PIO1 SM2–3 stay free.
* The program is 8 instructions and is loaded at offset 0 in both blocks
  (8 of 32 instruction slots used per block).
* Each state machine drives two pins: STEP by side-set, DIR by `out pins`.
  Pins on the same block don't need to be adjacent.

This allocation was checked to fit: 6 of 8 state machines and 16 of 64
instruction slots. Six-axis **CPU timing** is not yet measured (§9).

### Program

```text
0  pull block          side 0         ; wait for a command
1  out pins, 1         side 0 [S]     ; DIR, then setup delay
2  out x, 15           side 0         ; pulse count - 1
3  out isr, 16         side 0         ; low-time loop count L
4  pulse: nop          side 1 [H]     ; STEP high for H+1 cycles
5  mov y, isr          side 0
6  low: jmp y-- low    side 0         ; L+1 cycles
7  jmp x-- pulse       side 0
```

Command word: bit 0 = DIR level, bits 1–15 = pulses − 1, bits 16–31 = `L`.

### Timing

State-machine clock: 125 MHz / 25 = **5 MHz** (200 ns per cycle, integer
divider, no fractional jitter).

| quantity | cycles | time | configured by |
|---|---|---|---|
| STEP high | `H + 1` = 10 | 2.0 µs | `TIMING.high_cycles` |
| STEP low (min) | `L + 3` ≥ 10 | ≥ 2.0 µs | `TIMING.min_low_cycles` |
| DIR setup before first STEP edge | `S + 3` = 10 | 2.0 µs | `TIMING.dir_setup_cycles` |
| DIR hold after last STEP edge | `L + 4` ≥ 11 | ≥ 2.2 µs | follows from minimum low |
| fastest period | 20 | 4 µs (250 kHz) | high + min low |

All values are in `boards/rp2040/src/board.rs` (`TIMING`). Check them
against your driver's datasheet before changing anything.

### Windows, buffering and failure behaviour

* Tick window: 200 µs. Pulses may use 90 % of it (`window_budget_pct`); the
  rest absorbs command overhead and interrupt jitter.
* At most 44 steps per axis per window (220 kHz) at this timing. The board
  metadata advertises a conservative **50 kHz** per axis until hardware
  measurements justify more.
* The TX FIFO is joined (8 words); one window needs at most 4 words per axis.
* Before queuing a new window, the previous one must have been taken by the
  state machine (FIFO empty). Otherwise the output lags behind the tick and
  the firmware faults with `StepRateExceeded`, rather than letting the lag
  grow. The same fault is raised if a window's steps don't fit the timing.
* A tick gap longer than 10 windows (2 ms) during motion faults with
  `SegmentLate`. Queue underrun and late segments are detected by the
  shared stepper code as before.
* Disable / fault / E-stop: ENABLE goes high first, then the state machine is
  stopped, STEP is forced low, both FIFOs are cleared and the program is
  parked at `pull`. No queued pulse is emitted afterwards.
* Endstop reaction: the firmware checks the switch before every step, but the
  step reaches the pin up to one window (200 µs) later. Worst-case overtravel
  is the steps of one window: 1 step at 5 kHz, 10 steps at 50 kHz.

### Synchronisation between axes

All axes' commands for a window are queued by the same tick interrupt, one
after the other, so the windows of different axes start within a few
microseconds of each other (the push loop). Segment start times are absolute
MCU timestamps, as on every board. The skew still needs measuring (§9.1). This
is what coordinated joint moves (`MoveJ`) build on: the host plans every
joint on one time grid (`motion::plan_synchronized_scaled`), so the segments
of all axes carry the same start times.

## 5. Electrical

* RP2040 GPIO is **3.3 V and not 5 V tolerant.** Use step/dir drivers whose
  logic inputs accept 3.3 V (most TMC, DRV8825 and A4988 boards do), or add
  level shifters. Never connect a 5 V/12 V/24 V signal directly.
* Pin drive strength defaults to 4 mA. For long cables or opto-isolated
  driver inputs that need more current, add a buffer such as a 74HCT245
  powered at 5 V.
* **ENABLE needs an external pull-up** to the driver's logic supply, so the
  drivers stay disabled during reset, in BOOTSEL mode, during a watchdog
  reset, and with no firmware. The firmware drives ENABLE high (disabled)
  before configuring anything else.
* External step/dir drivers are required (e.g. TMC2209 in step/dir mode,
  DRV8825, A4988, or an external servo/stepper drive with step/dir inputs).
  The Pico must never power motors.

## 6. Endstop and E-stop wiring

* **Endstops:** normally-open switch between the ENDSTOP pin and GND. The
  internal pull-up is enabled, so pressed = low. For noisy environments add
  an RC filter (e.g. 1 kΩ / 100 nF) or use normally-closed switches with
  `invert = true` in the profile.
* **E-stop (mandatory):** a hardware E-stop circuit must **remove driver
  power** (contactor or safety relay) independently of all software.
* **Interlock monitor (GP27):** wire an auxiliary contact of the E-stop
  circuit (closed when it is safe to run) between GP27 and GND. While GP27
  is open:
  * the firmware latches an emergency stop and disables every drive,
  * `Enable` is refused, and
  * `ResetFault` is refused.

  An unconnected GP27 counts as open, which is the safe default. On a bench
  without an E-stop circuit, use a jumper to GND, and only with motors that
  cannot cause harm.

The interlock input only *monitors* the E-stop. It does not replace it.

## 7. Building and flashing

```bash
rustup target add thumbv6m-none-eabi          # listed in rust-toolchain.toml

motioncore firmware targets                    # boards, channels, flash method
motioncore firmware build --board rp2040-pico  # reference profile -> build/firmware/rp2040-pico/
motioncore firmware build --config my-robot.toml   # your own profile -> build/firmware/<mcu>/
```

A build writes `firmware.elf`, `firmware.uf2`, `manifest.json` (SHA-256 of
both images), `motioncore.lock.toml` and `build.log`. The UF2 is generated
from the ELF by the builder and validated block by block: magic numbers,
RP2040 family id `0xe48bff56`, block numbering, and every block inside the
2 MiB flash window starting with the boot2 stage at `0x10000000`.

### Flashing via BOOTSEL (UF2)

1. Disable the drives (`motioncore disable`) and remove driver power.
2. Hold **BOOTSEL** on the Pico while plugging in USB. A drive named
   `RPI-RP2` appears.
3. Run:

   ```bash
   motioncore firmware flash --board rp2040-pico --yes
   # or, if the drive is not found automatically:
   motioncore firmware flash --board rp2040-pico --uf2-volume /media/$USER/RPI-RP2 --yes
   ```

   The tool checks the artifact, refuses while a reachable engine reports
   enabled drives, copies `firmware.uf2` to the drive, and waits for the
   drive to disappear (the bootloader took the image and rebooted). If the
   drive is still there after 15 s, it reports failure: nothing is confirmed
   flashed.
4. Confirm what is actually running:

   ```bash
   motioncore firmware verify --board rp2040-pico --device /dev/ttyACM0   # COMx on Windows
   ```

   `verify` compares board, build hash and capabilities reported by the MCU
   with the artifact. Only this step confirms a successful flash.

### Flashing via SWD (optional)

With a debug probe (e.g. a second Pico running debugprobe):
`probe-rs download --chip RP2040 build/firmware/rp2040-pico/firmware.elf`.
`cargo run` inside `boards/rp2040` uses the same runner.

## 8. Configuration example

`robot-profiles/six-axis-rp2040-pico.toml` is the reference profile (six
revolute axes, endstops, homing). One axis:

```toml
[mcu.main]
board = "rp2040-pico"
transport = "serial:///dev/ttyACM0"
watchdog_ms = 500

[[axis]]
id = "j2"
kind = "revolute"
unit = "deg"
mcu = "main"
channel = 1
steps_per_unit = 44.444444
min = -90.0
max = 90.0
max_velocity = 45.0          # 2000 steps/s, below the 50 kHz board limit
max_acceleration = 180.0

[axis.driver]
actuator = "org.motioncore.actuator.step_dir"
step_pin = "GP2"             # must match the firmware pin map (§3)
dir_pin = "GP3"
enable_pin = "GP13"

[axis.endstop]
pin = "GP19"

[axis.homing]
direction = "negative"
speed = 15.0
position = -90.0

```

## 9. Hardware validation

None of the following has been carried out yet. Run them with the bench
session guide, [`validation/rp2040-bench-session.md`](validation/rp2040-bench-session.md)
(order, builds, timing profile, analyser channels), record the results in a
copy of [`validation/rp2040-record-template.md`](validation/rp2040-record-template.md),
and summarise them here (date, board, driver, firmware build hash).

Equipment: logic analyser with at least 24 MHz sample rate on 8 channels (or
an oscilloscope), a Pico flashed via §7, step/dir drivers **without motor
power** for the timing tests.

Use a temporary debug build that toggles a spare GPIO (e.g. GP28) at the
start and end of `TIMER_IRQ_0` to measure interrupt timing.

| # | Test | Procedure | Pass criterion |
|---|---|---|---|
| 1 | Safe start | Power up with and without firmware, in BOOTSEL, during flashing | All ENABLE lines high throughout |
| 2 | Identity | `motioncore firmware verify` | board `rp2040-pico`, build hash matches |
| 3 | STEP high time | Jog one axis at 1, 10 and 50 kHz | 2.0 µs ±0.1 µs |
| 4 | STEP low time | Same captures, shortest low phase | ≥ 2.0 µs at every rate |
| 5 | DIR setup / hold | Reversing move; DIR edge to next STEP rise, last STEP fall to DIR edge | ≥ 2.0 µs / ≥ 2.2 µs |
| 6 | Frequency accuracy | Constant-velocity jog; count edges over 1 s | within 0.1 % of commanded, exact total step count |
| 7 | Jitter | Histogram of STEP periods at constant velocity | spread ≤ one 200 µs window boundary effect; no periods below minimum |
| 8 | Max sustainable rate | Raise rate until `StepRateExceeded` | record; keep advertised limit ≤ 50 % of it |
| 9 | Six axes simultaneously | All six channels at 50 kHz | no fault; tick ISR (GP28) < 100 µs |
| 10 | Stop latency | `estop` during motion: command on USB to last STEP edge and ENABLE high | ENABLE high and STEP stopped within 1 ms of frame receipt |
| 11 | Watchdog | Unplug USB while enabled | ENABLE high within 500 ms |
| 12 | Hang | Halt core 0 with a debugger (watchdog pause on debug off) | reset within ~100 ms, ENABLE high |
| 13 | Interlock | Open GP27 while moving | `EmergencyStop` fault, drives disabled, reset refused until closed |
| 14 | Endstop | Home each axis at low speed | trigger detected, overtravel ≤ 1 step at homing speed |
| 15 | Coordinated-move skew | One six-axis `movej`, analysed with `tools/step-skew` (§9.1) | skew ≤ 50 µs, constant over the move; every edge within one window + 1 step of its ideal time (tool defaults); recorded |
| 16 | Panic safe state | Firmware built with `--features bench-panic`; during a six-axis move tie GP28 to GND | ENABLE high and no further STEP edge within 10 µs of the trigger; watchdog reset after ~100 ms; engine faults on the lost link |

Only after 1–16 pass: connect motors with low current limits and no load,
then jog ±1°, home, stop mid-move and E-stop.

### 9.1 Coordinated-move skew (test 15)

What it measures: how far the STEP output of each channel lags or leads the
others during a coordinated joint move. The host plans every joint on one time
grid and the tick interrupt queues the windows of all axes one after another,
so the offset between channels should be a few microseconds, constant over the
move.

1. Flash the firmware (§7) and wire all six STEP outputs (GP0, GP2, GP4, GP6,
   GP8, GP10) to the logic analyser; drivers **without motor power**, or no
   drivers.
2. Start the engine with `robot-profiles/six-axis-rp2040-pico.toml`, close the
   GP27 interlock, `motioncore enable`, then `motioncore home-all`, closing each
   endstop input by hand (jumper to its active level) when its axis is
   searching. Every axis ends at its negative limit.
3. Start the capture (≥ 24 MHz), then run one coordinated move in which every
   axis moves a different distance in one direction:
   ```bash
   motioncore movej j1=0 j2=0 j3=-35 j4=60 j5=-10 j6=90
   ```
4. Export the capture as CSV and analyse it:
   ```bash
   python tools/step-skew/step_skew.py capture.csv --step D0,D2,D4,D6,D8,D10
   ```
   The tool reports each channel's offset and jitter (in µs and in steps)
   relative to the channel with the most steps, and fails an edge that
   deviates more than one window plus one step at its local step rate
   (`tools/step-skew/README.md` explains the method).
5. Record the offsets, the skew (largest minus smallest offset), the jitter
   (µs and steps), the firmware build hash and the date here. Repeat with
   `--speed 0.25` and at the maximum rate of test 8.

## 10. Known limitations

* Not yet run on hardware: flashing, USB enumeration, pulse timing, six-axis
  CPU budget and stop latency are **unverified**.
* Step timing resolution is one 200 µs window. Steps are evenly spaced
  within a window, not placed at their exact ideal times (deviation < 1
  window).
* Endstop and fault reaction can trail the commanded position by one window
  (§4).
* Advertised step rate is a conservative 50 kHz per axis until measured.
* Single MCU per robot; coordinated joint moves are tested in simulation
  only.
* Only the Pico's W25Q080 flash (2 MiB) boot2 is included. Boards with other
  flash chips need a different boot2.

## 11. STM32F411 compatibility

* The STM32F411 firmware, pin map, probe-rs flashing and artifacts are
  unchanged. `Hal::flush_pulses` defaults to a no-op, so its pulse path is
  unchanged too.
* `firmware build --config robot-profiles/single-axis-stm32f411.toml` still
  writes to `build/firmware/main/`. `firmware build --board
  stm32f411-blackpill` is new and writes to
  `build/firmware/stm32f411-blackpill/`.
* The resolver now also checks STM32 profiles against its fixed pin map
  (channel 0: PA0/PA1/PA2/PB0), which the shipped profile already matched.
* The engine now refuses an MCU whose reported board differs from the
  configuration (for example a Pico connected where an STM32 is configured).
